## 1. What this is and who it's for

PyGCGC processes GC×GC-EI-ToF-MS data. It is a Python package (`pygcgc.core`, no GUI dependencies) plus a PySide6/pyqtgraph desktop app (`pygcgc.gui`).

The user is James Brean, an atmospheric chemist at the University of Birmingham.

**Instrument.** An older Markes/SepSolve GC×GC with a 70 eV EI time-of-flight MS (BenchTOF family, unit mass). Samples are thermally desorbed from Tenax tubes. ChromSpace is the vendor software, and data leave it as ANDI/AIA `.cdf`.

**Target compounds** (from James's calibration scheme; the dummy data mirrors it):
- n-alkanes, PAHs, nitro-PAHs and 2-octadecanone, from 100 µg/mL stocks
- oxy-PAHs, from 10 µg/mL stocks
- decalin, two cycloalkanes and behenic acid, from 1000 µg/mL stocks
- deuterated internal standards

The calibration has 8 levels, the first of which is an internal-standard-only blank.

**The internal standard and cycloalkane identities in the dummy data are placeholders.** James's answers (section 10, Q2-3, 2026-09-19): there are many internal standards and which ones apply depends on the sample/method, so a maintained list is needed, and the default IS-pairing rule should be the nearest internal standard by normalised (t1, t2) distance rather than a fixed per-target assignment (see section 7). "Cycloalkanes 1 and 2" are not two specific compounds -- they stand in for a large number of different cycloalkanes from C10 upwards, which doesn't matter for the software's fundamentals (any name/RI works for these rows). The actual internal-standard list (names, concentrations, which targets pair with which) is still needed before building a real `target_table.csv`.

## 4. First job with real data

Work through this in order and report findings to James before changing defaults.

1. **Summarise the files.** Run `pygcgc info` on a few runs and look at:
   - scan count and rate (expect tens of Hz)
   - start time and units (seconds are expected; the reader converts minutes if the `units` attribute says so)
   - the m/z range
   - the number of stored points
   - the timing report
   - any warnings (a high-resolution warning means masses are not unit)
2. **Check what ChromSpace actually exports.** The reader assumes the *unfolded* detector stream with all masses: one scan per acquisition time, centroids in `mass_values` and `intensity_values`, and `point_count` or `scan_index`. If the export is folded, TIC-only, profile-mode or split across files, the reader in `core/io/andi.py` needs adapting. Open a file with `netCDF4.Dataset` and list its variables and global attributes. Record anything unexpected in this file.
3. **Encoding details.** Check:
   - `mass_values` dtype and any `scale_factor` (auto-applied)
   - whether intensities are integers
   - whether stored values have a clear lower threshold (`core/background.storage_threshold`)
   - whether any stored values are negative or NaN (the reader drops them)
4. **Modulation period.** Get it from James or the method (it isn't in the ANDI file) and put it in `method.json` next to the data.
5. **Make a real target table and levels file.** Open a run in the app, find the internal standards, and note their apex t₁ (absolute seconds) and t₂. Build `target_table.csv` with `role=istd` rows. Then run `pygcgc phase ... --targets target_table.csv` across a sequence. Check that:
   - anchors are found in most runs
   - the phase spread is a few ms
   - the period check is "not significant"

   A significant period correction on real data is interesting: ask James before applying it.

   James plans to run standards of known composition and concentration as calibration sequences. Build `calibration_levels.csv` from his dilution scheme (one row per level, one column per compound, amounts in the unit he wants results in), and add `cal_set` and `volume_m3` columns to `sequence.csv` if there is more than one calibration block or if samples have air volumes.
6. **Visual check against ChromSpace.** Run `pygcgc fold RUN.cdf --period P --targets ... --extend 1.15 --png check.png` and compare with ChromSpace's own 2D plot: orientation, t₂ range, wrap-around and the positions of known compounds.

## 5. Architecture and rules

- **`pygcgc.core` never imports Qt.** All science goes there, is tested there, and is callable from scripts and the command line. The GUI only calls into it.
- **The GUI thread only draws and handles input.** Anything slow is a job: `gui/jobs.JobManager.submit(name, fn(token, progress), on_done, on_error, latest_key=None, quiet=False)`.
  - `latest_key` makes newer requests cancel older ones (live previews, rendering).
  - `quiet=True` keeps a job out of the Jobs panel.
  - Signals are emitted from worker threads and delivered on the main thread.
- **Views never fold data themselves.** They ask `Project.fold(i)` and `Project.display_run(i)`, and the `Renderer` builds images off-thread with an LRU cache and preloads neighbouring runs.
- **Processing is non-destructive.** A processing step is a *layer* that produces a new `Run` (same sparse structure where possible) plus metadata. Raw runs never change.
  - `RunEntry.background` holds the applied 🧹 layer, `RunEntry.siloxane` the applied 🫧 layer (built on whatever 🧹 left, or raw if there's no 🧹), and `Project.preview` holds a preview.
  - `Project.result_for(i)` decides what is shown: a preview first, then 🫧 if applied, then 🧹 if applied, otherwise raw. Anything reading `entry.background` directly (🧪's own measurement does) skips 🫧 entirely; only what goes through `result_for`/`display_run` (the view, 🔍) sees it.
- **Undo** holds processing changes only: phase, period, 🧹 and 🫧 apply and remove. View settings (zoom, levels, ion, scale) are deliberately excluded.
  - Commands for work done asynchronously (`SetPhases`, `ApplyBackground`, `ApplySiloxane`) are pushed *after* the result is applied, and skip their first `redo`.
  - The undo stack is cleared when runs are removed, because snapshots refer to run positions.
- **Derived layers follow their inputs, except 🫧, which is simply cleared.** A phase or period change triggers recomputation of that run's 🧹 layer, or of every run's layer if the blank moved (`Project._fold_changed`); applying, changing or removing 🧹 also recomputes it (`set_backgrounds`). A 🫧 layer built on top of either is invalidated by both, but only by being set back to `None` rather than refit, since refitting would mean chaining another background job after whichever one just ran. Re-apply 🫧 (one click) after moving the fold or changing 🧹.
- **🧪 lives in `gui/quantstate.QuantState`** (owned by the project). It keeps `RunQuant` results per `RunEntry`, the settings, and the review decisions (`core/quant.QuantDecisions`). Decisions only need the fast final step (`finish_sequence`) again, except a peak picked by hand, which re-measures that one run. `EditDecisions` pushes a before/after copy of the decisions. Results are never saved; they are rebuilt from settings and decisions on load. Phase, period and 🧹 changes mark results stale (banner in the Results panel); they are not rerun automatically.
- **🔍 lives in `gui/blob_state.BlobState`** (owned by the project as `project.blobs`), independent of 🧪 (which finds its own copy of the same blobs internally on its own settings). It keeps one `BlobSet` per `RunEntry` and a small positional edit log (delete/merge/add) per run name. Like 🧪, results aren't saved; a settings or fold/🧹 change marks a run stale (`stale`, a set of `RunEntry`), and a settings change additionally clears the edit log (see section 7 for why). `EditBlobs` pushes a before/after `(RunEntry, BlobSet, edit list)` snapshot, the same shape as `EditAlignment`.
- **🫧 lives directly on `Project`** (`siloxane_settings`, `RunEntry.siloxane`, `compute_siloxane`/`set_siloxanes`/`siloxane_snapshot`), not in its own state class like 🧪/📍/🔍 -- there's no per-run edit log, review workflow or hand-editing to justify one, just a settings blob and a per-run result, so it follows 🧹's own shape (`bg_settings`/`set_backgrounds`) instead. If 🫧 grows a settings dialog or its own diagnostics panel, revisit whether it still fits directly on `Project` or deserves `SiloxaneState`.
- **✂️ lives directly as a self-contained GUI dialog (`gui/overlap_dialog.OverlapDialog`), not part of `Project` state, the same reasoning as 🗂️ (below).** It picks one blob from whichever run's `BlobSet` the main window hands it (`set_run`), analyses it, and shows the result -- there's nothing to save (a fit or an MCR-ALS decomposition isn't a layer or an edit) and nothing to undo. It doesn't track a run switch live: reopening it (the toolbar button) is how it picks up whichever run is now open, the one deliberate simplification against the batch dialog's own precedent (which needs no such refresh, since it's tied to a folder, not "whichever run is open").
- **⛓️ lives in `gui/hydrocarbon_state.HydrocarbonState`** (owned by the project as `project.hydrocarbons`). Finding or propagating the alkane ladder isn't undoable, the same reasoning as 🔍's `find_blobs`: it's a detection result (one `AlkaneSeries` per `RunEntry`, not saved, rebuilt on demand), not an edit. Stencils (`StencilSet`, one frame) are the edit layer, and *are* saved -- `EditHydrocarbons` pushes a before/after copy of the whole `StencilSet`, the same shape as `EditAlignment`/`EditBlobs`. A stencil means the same thing on any run precisely because it's recorded in alkane-relative coordinates rather than absolute t1/t2 (see `core/hydrocarbons.py`'s module docstring); that's also why the series itself doesn't need to follow fold/🧹 changes the way 🫧 does -- a stale series just needs re-finding, it doesn't silently mis-lift a stencil, because `AlkaneSeries.to_absolute` always reads through whichever series is current.
- **🏷️ lives directly as a self-contained GUI dialog (`gui/identify_dialog.IdentifyDialog`), not part of `Project` state, the same reasoning as ✂️ and 🗂️.** The loaded `Library` is dialog-local (not per-run, not saved with the project -- reload the MSP file next session); the search results are a plain list shown in a table, nothing to undo. Its two write actions (`promote_to_file`, `add_to_inhouse_file`) don't touch the Project directly either: they write a target-table CSV or an MSP file to disk and tell the user to reload it, the same "write a file, don't mutate live state" shape 📤's report export already uses, rather than reaching into `Project`/`QuantState` to add a target on the fly.
- **🗂️ lives directly as a self-contained GUI dialog (`gui/batch_dialog.BatchDialog`), not part of `Project` state at all.** Unlike 🧪/📍/🔍/⛓️, it isn't a per-run layer with an undo history or a save/reopen story to fit into `Project.to_dict` -- it's a one-shot, folder-level analysis (pick a folder, run it, look at the results) with nothing to persist or undo. Its only touch point with the rest of the app is `navigateRequested`, a signal `MainWindow._batch_navigate` uses to jump the main window to a run and t1/t2 the user double-clicked or point-clicked inside the dialog, exactly the same "reach back into the main window" shape 🧪's Review gallery and 📍's Compare view already use.
- **📤 has no GUI state class at all, and no place in `Project.to_dict` either.** `core/report.py` is plain functions (`build_provenance`, `write_excel`, `write_html_report`, `write_pdf_report`, the `plot_*` chart builders), called directly from `gui/batch_dialog.py`'s export button and from `cli.py`; there's nothing to own between calls. `build_provenance` accepts 🔍's edit log, 🧪's decisions and ⛓️'s stencils as optional arguments precisely so a future caller that *does* have Project state (a "report the run open right now" action, say) can pass them in without changing the function -- the batch dialog and the CLI just don't have that state available, by the same reasoning as the previous bullet, so they always pass none of it.
- **The left-hand column is a `WorkflowPanel`** (`gui/workflow.py`), not a set of docks. New tools go in as a step: build the settings widget, call `add_step`, add a `step_actions` entry and a `go` mapping, and call `workflow.mark_done` when the work finishes.
- **Projects** are JSON (`Project.to_dict`/`load`). Saved phases are kept; layers are rebuilt from their saved settings on load.
- **File access is serialised** with a lock in `core/io/andi.py`, because the netCDF/HDF5 C libraries aren't guaranteed thread-safe. An unguarded threaded read once produced an intermittent failure.

## 7. Decisions worth knowing (and why)

- **No period estimate from the chromatogram alone.** Adjacent-column similarity was far too flat to locate the period, and block-drift tracking was off by several ms on sparse runs. More fundamentally, a genuine t₂ drift is indistinguishable from a period error. The period comes from the method; anchors check it (`period_from_anchors`, with a standard error and a significance flag).
- **Phase on shifted samples absorbs the run-wide t₂ shift.** That's intended: it aligns runs to expected positions. The dummy calibration runs recover the true phase to within 20 ms; samples to within 50 ms.
- **Void-method phase is a display cut only.** It finds a cut that splits no peaks, but it can't tell where the modulator cycle truly starts. It is used only when no run in the sequence has usable anchors; otherwise such runs borrow the circular median phase of the others.
- **Background percentile bias correction.** A low percentile sits below the middle of the noise. The code measures the noise spread from the gap between the p-th and (p/4)-th percentiles and raises the estimate by the Gaussian offset, and does the same for the stripe pattern. Without this, cleaned bleed ions sat about 4 counts above zero.
- **Stiffness default of 1e4, scaled with run length.**
  - On a 465-modulation run, 1e5 couldn't follow a steep bleed rise, and 1e3 ate a few per cent of a large tailing peak (behenic acid at the lowest level). 1e4 keeps behenic acid within about 3%, and handles realistic bleed.
  - The arPLS penalty grows with the fourth power of the number of points, so the setting is multiplied by (modulations / 465)⁴ before use (`REFERENCE_COLUMNS`). Without this, the 60-modulation synthetic test runs were far too stiff and left a curved bias.
- **The repeating-pattern step only looks at complete modulations.** A partly recorded modulation has empty rows that look like a deep dip. Letting it into the rolling window over-subtracted the last few seconds of a run by tens of counts. Incomplete modulations now borrow the pattern of the nearest complete one.
- **Spikes are replaced by the median of their four neighbouring scans**, which is usually zero. Zeroing them outright lost a little real signal when a spike landed on a peak tail.
- **Only ions with background are processed.** An ion needs at least 80% of a modulation's rows filled; this is what keeps a run under about a second. Noise is measured on those ions; the rest get the floor.
- **Blank subtraction never takes a point below zero** and scales per ion. This is a known compromise when artefacts share ions but vary independently. Per-peak scaling should come with blob detection (milestone 6).
- **Colour levels lock by default** when flicking, so runs are comparable. For log scale on cleaned data, auto levels start at the 90th percentile, because most pixels are noise around zero.
- **A preview overrides Space** (the raw/cleaned toggle), because it is its own mode.
- **Ratio images use a floor** (denominator above 20 counts) to avoid noise blow-ups, and switch the scale to linear.

- **Positions are learned from the calibration runs** (`learn_positions`), then each target is also moved by its internal standard's shift in that run. Table positions only need to be roughly right.
- **Two response kinds per target.** The quantifier-ion ratio quantifies the target. The whole-peak (TIC) ratio, fitted too, is what stands in for nearby unknowns, because an unknown has no quantifier ion of its own.
- **"Nearest" is a scaled 2D distance** (60 s of t₁ = 0.5 s of t₂). The target table's `istd` column overrides it for targets. James asked for every signal to be reported relative to the nearest internal standard; that is the All signals table (`ratio`). Confirmed again independently (section 10, Q2, 2026-09-19): with many internal standards in real sequences and which ones apply varying by sample, James wants the normalised-distance nearest-IS rule as the *default* everywhere, not just for the All signals table. Worth revisiting whether `target_table.csv`'s `istd` column should itself default to the nearest IS automatically rather than needing a person to hand-assign one per target, now that real sequences are expected to carry more internal standards than the dummy data's placeholder set.
- **Semi-quant amounts are labelled and capped.** Only within `surrogate_max_distance` (3 units) of a calibrated target, reported "as" that target, in their own table. They were requested as "apply the calibration to nearby peaks"; the assumption that neighbours respond alike is stated in the README.
- **Calibration sets come from an explicit `cal_set` column.** A sample uses its own set, otherwise the most recent set above it in the sequence. Bracketing interpolation for drift was discussed but not built.
- **TIC blob footprints are trimmed to 1% of their own apex** (`blob_rel_floor`). Without this, footprints in the UCM hump spread over hundreds of noise pixels and volumes were inflated.
- **The noise floor comes from the raw file** (its storage threshold). Computing it from a cleaned run gave a floor near zero, because cleaning leaves tiny positive values.
- **R² is shown but never used for decisions**; weights are chosen by relative error, curvature by Mandel's test.

- **Blob detection takes the maximum of the TIC-S/N and ion-summed-S/N surfaces, not just the ion sum.** An earlier version switched over entirely; on a run with only a couple of active ions this occasionally under-performed the plain TIC method it was meant to improve on, because a single ion's own noise estimate is noisier than the noise estimate of a bigger, brighter TIC image. Taking the max keeps every guarantee the old method had and only ever adds sensitivity.
- **Co-elution clustering uses `scipy.cluster.hierarchy.fclusterdata`, not DBSCAN.** scipy is already a dependency and scikit-learn isn't; for the handful of ion-apex points inside one blob's footprint, single-linkage clustering with a distance threshold behaves the same as DBSCAN would.
- **Blank subtraction scales per connected region of one ion's own significant pixels, not per TIC blob.** Reusing the TIC `BlobSet` was considered and rejected: it would need `find_blobs` run on the blank as a prerequisite, cross-module coordinate reconciliation (the TIC blob frame is extended for wrap-around; the plain per-ion image background.py already works with isn't), and a TIC blob could bundle two DIFFERENT ions' artefacts together anyway if they happen to co-elute in the TIC. A plain `scipy.ndimage.label` on that one ion's own significant-pixel mask is simpler, self-contained, and exactly the right granularity for "two artefacts on the same ion varying independently between tubes."
- **The 🔍 edit log (delete/merge/add) is positional and is cleared on a settings change, but kept across a fold or 🧹 change.** `find_blobs`'s output order is stable for the same settings and data, so "delete blob 3" replays correctly after e.g. re-cleaning; it isn't guaranteed to mean the same thing after the detection surface itself changes, so a settings change starts the log over rather than risk silently misapplying it.
- **🫧 removal needs a per-pixel goodness-of-fit gate, not just a presence-count gate.** The spec's literal wording ("fewer than N siloxane ions present -> don't fit") protects an isolated single-ion peak, but not a real three-ion coincidence in the wrong proportions: a least-squares fit across a handful of ions is pulled toward whichever ion the reference weights most, so the *dominant* ion can still get subtracted to nothing even when the ratios plainly don't match. Requiring the pixel's own ion ratios to resemble the reference (a per-pixel cosine similarity, `min_fit_cosine`) closes that gap; `test_a_real_coincidence_in_the_wrong_ratio_is_not_removed` is the test that found it needed closing.
- **🫧 removal only needs `Run`/`Fold` (via `Fold.cube`), never a `BlobSet`.** Only the separate *flagging* half of the milestone (scoring blobs) touches `core/peaks.py` at all. Keeping removal blob-free means it can run on any run regardless of whether 🔍 has ever been used on it, and `core/siloxane.py` doesn't need to import the wrap-aware `Frame` machinery peaks.py carries.
- **The n-alkane search reuses `phase.locate_anchor` rather than a bespoke ion-image search.** It already does exactly what's needed -- brightest pulse of an ion within a window of an expected *absolute* time, refined to sub-scan precision -- because a genuine internal-standard or alkane peak is normally the tallest thing on its own ion near where it's expected; there was no need to build a second, 2D-windowed search just because the caller this time is an alkane, not an internal standard. The window is generous (6 s default) precisely because the "expected position" fed in is a mid-modulation `t1` (up to half a period off the true absolute apex time, the same approximation `align.propagate_anchors` already relies on for its own reported `run_t1`), not because the alkane's real position is that uncertain.
- **A stencil is recorded in (carbon number, t2 offset from the alkane line), never in absolute t1/t2**, which is the entire reason lifting it onto another run works: `Stencil.to_absolute` reads the SAME two numbers back out against whichever `AlkaneSeries` you hand it. Storing a stencil's real coordinates alongside a "this was drawn on run X" note, and transforming between runs some other way (e.g. through 📍 alignment), was considered and rejected -- it would need every run aligned to the one the stencil was drawn on first, whereas alkane-relative coordinates need only that run's own ladder, found independently.
- **Group-type stencils and 📍 alignment solve superficially similar problems (map a shape from one run onto another) with deliberately different machinery**, and that's a feature, not duplication: alignment maps a whole 2D image via a fitted geometric transform from a handful of anchors anywhere in the run; a stencil maps a small polygon via one specific, always-available reference structure (the alkane ladder). Building stencils on top of `AlignmentTransform` would have made drawing one depend on first aligning every run to a shared reference -- an extra, avoidable step for a workflow (comparing a sample's hydrocarbon smudge to the alkane standard's) that doesn't otherwise need alignment at all.
- **Batch quantification reuses `quantify_prepared` rather than reimplementing calibration-across-a-batch.** `core/quant.py` already does everything the pipeline needs (target scoring, calibration fits, bracketing, all-signals) for one already-prepped set of runs; `run_batch`'s own job is entirely upstream of that (parallel prep, caching, resumability) and downstream of it (the feature table, QC, PCA, volcano), not a second, parallel implementation of quantification itself. If quant logic ever needs to change, it changes in one place regardless of whether it's called interactively or from a batch.
- **Caching starts at background removal, not at the read step.** Reading a run (`core/io/read_many`) is already threaded and fast relative to background removal, siloxane fitting and blob detection; caching it too would mean hashing a raw file's own bytes (or trusting mtime/size, which OneDrive sync can perturb without a real content change) for very little saved time. The chain hash instead starts from a cheap identity for the *raw* run (`_run_cache_base`: source path plus mtime/size, or nnz/sum of the sparse data as a fallback if those aren't available) and each subsequent step's cache key folds in the previous step's key plus that step's own settings, so changing one setting invalidates that step and everything after it, but nothing before it.
- **`max_workers <= 1` runs the exact same `_prep_one` function in a plain for-loop, not `ProcessPoolExecutor` with one worker.** A process pool has real overhead (pickling the run and settings, a new process, unpickling the result) that a same-process call doesn't, and a single worker gets none of the parallelism benefit to offset it. Every test in `test_batch.py` uses `max_workers=1` for exactly this reason: fast, deterministic, and it exercises the identical prep/caching logic the real process-pool path uses (`_prep_one` is a plain top-level function either way, which is also what makes it picklable for the pool path when workers > 1).
- **The feature table's gap-fill is a small, direct TIC integration (`_box_sum`), not a second pass of blob detection.** A run genuinely missing a peak the reference run has (below its own S/N threshold, say) won't produce a blob there no matter how blob detection is re-run; reading a small fixed window (6 s in t1, 0.15 s in t2 by default) of that run's own `.clean`/`.fold` TIC at the reference's position always gives a number, honestly close to zero (or to noise) when nothing is really there, rather than leaving a gap that would otherwise read as "unknown" instead of "not detected."
- **Provenance's manual-edit log is a generic mechanism, built and tested against synthetic edits, but wired to nothing real yet.** `build_provenance` takes 🔍's `BlobState.edits`, 🧪's `QuantDecisions` and ⛓️'s `StencilSet` as optional arguments and summarises whichever are given; every shipped caller (the batch dialog, both CLI commands) passes none of them, because 🗂️ is deliberately outside the per-run `Project` that accumulates that state (see section 5). This isn't a gap that needs filling before the mechanism is "real" -- `tests/test_report.py` exercises it directly with synthetic `blob_edits`/`quant_decisions`/`stencils` dicts and objects, which is a perfectly good test of "does the summary come out right," independent of whether any GUI action happens to call it that way yet. Wiring it into an actual interactive report action is separate, future work.
- **The GUI's 📤 export writes exactly what the tabs are already showing, not some independent default.** `BatchDialog._do_export` reads `self.qc_combo.currentData()` and the two group list widgets' current selections, the same state `_draw_qc`/`_draw_volcano` already use to draw the on-screen charts, rather than picking its own "first internal standard" or "first two runs" -- so what a person exports always matches what they were just looking at. The CLI has no screen to match, so it falls back to the first internal standard found and whatever `BatchConfig.group_a`/`group_b` say (see the next bullet).
- **`BatchConfig.group_a`/`group_b` existed since milestone 11 but were dead: nothing read them.** They were added to the saved-pipeline JSON schema for the volcano plot but only the GUI's own list-widget selections were ever wired to `volcano()`; a saved pipeline's groups did nothing. Milestone 12's CLI report wiring (`pygcgc batch --report ...`) is the first thing that actually reads them, making a scripted volcano plot possible for the first time. If a saved pipeline's volcano groups still seem to do nothing somewhere, check that code path is actually reading `config.group_a`/`group_b`, not assuming milestone 11 already wired it up.
- **Every plotting function in `core/report.py` is matplotlib, never pyqtgraph, on purpose.** The GUI's batch dialog already draws QC/PCA/volcano with pyqtgraph, live and interactively; `core/report.py` draws the *same* three charts again, deliberately separately, because core can't import Qt and a headless CLI/script run needs the identical chart without a display. The two implementations necessarily draw the same data slightly differently (different libraries, different exact pixel layout) -- that's an accepted, permanent duplication, not a TODO to unify, for the same reason `pygcgc fold --png` already draws its own matplotlib version of what the 2D view shows live.
- **A hand-built `BlobSet` (no `find_blobs` involved) was the right way to test ✂️, not fighting the automatic watershed into producing a merged footprint on demand.** `core/overlap.py`'s functions only ever need a `BlobSet`'s `labels`/`spectra`/`mz`/geometry fields, not anything about how it was produced; `tests/test_overlap.py`'s `_hand_blob` builds one directly from two synthetic peaks placed a few rows apart on different ions, with the footprint given as a plain rectangle, giving full control over the overlap scenario instead of tuning `PeakSettings` and hoping the watershed merges (or doesn't merge) the way a test needs. Worth remembering for any future test that wants a specific `BlobSet` shape: build one by hand rather than reverse-engineering detection settings to produce it.
- **The overlap fit now counts spectral coefficients in BIC and uses one weighted objective throughout.** The first real crowded-region audit showed that the earlier permissive BIC and unweighted inner NNLS were not defensible defaults. `fit_overlap` now uses the Poisson-style weights in both the inner spectral solve and outer residual, optionally fits a signed local background while keeping compound spectra non-negative, supports repeated starts, and counts spectral coefficients in the penalty. Likelihood improvement is capped once residuals fall below the variance implied by the weights, preventing redundant components from fitting numerical interpolation error in noiseless synthetic data.
- **PARAFAC2, not just PARAFAC, was scoped out, for the same reason the siloxane ROC threshold and the alkane qualifier-ratio gate are still provisional.** PARAFAC assumes every run's own elution profile for a compound has the same *shape* (only scaled); PARAFAC2 relaxes that to allow retention-time drift between runs, which is more realistic but needs materially more machinery (a per-run correction, not just three factor matrices) to build correctly. Building it against nothing but synthetic data risked getting the API and the drift model wrong in ways only real multi-run drift could actually expose -- better to build PARAFAC properly, prove the diagnostics (`core_consistency`, `split_half_stability`) work, and revisit PARAFAC2 once there's real data showing runs drift enough to need it.
- **The numerically stable form of the EMG (exponentially modified Gaussian) uses `scipy.special.erfcx`, not `erfc`.** The textbook formula `(1/2τ)·exp(σ²/2τ² − (x−μ)/τ)·erfc(v)` overflows `exp(...)` for a small tail constant τ, before `erfc` gets a chance to shrink it back down. Substituting `v = (σ/τ − (x−μ)/σ)/√2` and factoring out `exp(v²)` from the exponential turns `exp(...)·erfc(v)` into `exp(-0.5u²)·erfcx(v)` (where `erfcx(v) = exp(v²)·erfc(v)`, computed directly and stably by `scipy.special.erfcx` without forming either large intermediate), derived by hand and checked against the naive formula on values away from the overflow region before trusting it. `core/overlap._emg_1d` uses this form; a naive `erfc`-based version would silently return `inf`/`nan` on tailing peaks with a short time constant.
- **A library is a sparse (entries, unit mass) matrix, `core/quant.py`'s existing style of a dense-in-spirit per-mz array applied at library scale, not a fresh design.** `build_library` precomputes each entry's own top ions at load time (once), not on every search -- consistent with the rest of this codebase's habit of doing the expensive vectorisable pass once up front (`_active_ion_cube`, `BlobSet.spectra`) rather than per-comparison.
- **Search is a query spectrum against a whole library, prefiltered before any real scoring happens.** Two cheap tests (RI window, at least one shared "top ion") run first over every library entry; the actual weighted dot product (`_score_one`) only runs on whatever's left, which for a real library is a handful of entries, not thousands. This matters more than it sounds: a full pairwise weighted dot product against every entry, for every blob, is the part that would actually be slow against a real multi-thousand-compound library, and there was no way to check the real cost without one -- the prefilter is there so the design doesn't fall over the day a real library is finally plugged in, not because it was measured to be necessary against synthetic libraries of a dozen entries.
- **Target-decoy competition (`assign_qvalues`) runs across a whole batch of best hits (every blob on a run), not per query.** A single query's own score has no absolute meaning on its own -- "how good is 0.75?" depends entirely on how the whole scoring function behaves on real and decoy spectra alike. Competing every query's single best hit against every other query's, decoys included, is what turns a raw score into an actual estimated false discovery rate; scoring one blob in isolation (as `search` alone does) can rank its own candidates against each other, but can't say anything about how trustworthy the winner is. This is exactly why `identify_blobs` calls `assign_qvalues` once, on the whole run's results, rather than leaving it to be called per hit.
- **`Target.ri` (`core/targets.py`) already existed before this milestone -- it's not new.** The target table format was designed with a retention-index column from early on, well before milestone 9 built anything that could populate it automatically; `promote_to_target` is simply the first thing that actually fills it in from real data rather than a person typing a number into the CSV by hand. Worth knowing so a future reader grepping for "when was `ri` added" doesn't go looking in the wrong milestone.
- **The confidence tiers (`classify`) are a simplified reading of Schymanski and colleagues (2014), not the real five-level scheme, and the module docstring says so up front rather than letting the tier labels imply more than they mean.** A unit-mass EI spectrum plus a retention index can support "probable structure" (2a/2b) or "tentative candidate" (3) reasoning, but level 1 needs an actual co-injected reference standard (the closest this pipeline gets is `promote_to_target`, which still needs a person to accept the ID) and level 4 needs an exact-mass molecular formula this instrument's unit-mass detector can't give. Returning `None`/2a/2b/3 rather than inventing a 1 or a 4 keeps the tier label honest about what unit-mass EI-MS plus RI can and can't establish.

## 8. Gotchas

- pyqtgraph is configured with `imageAxisOrder="row-major"` in `views/image2d.py`; images are `(rows, modulations)`.
- **Qt in tests:**
  - set `QT_QPA_PLATFORM=offscreen`
  - `qtbot.waitUntil` callbacks must return a bool; returning a list raises an error
  - use `QTimer.singleShot(ms, context_object, fn)` so timers die with their widget
- `RunEntry` is `@dataclass(eq=False)` so entries compare and hash by identity. Several dicts are keyed by entry.
- `Run` is also `eq=False`; `run in list` would otherwise compare arrays.
- `Renderer` cache keys include `id()` of the raw run and the layer result. A new result object means a new image.
- `percentile_filter` is the slowest part of background removal. If runs get much longer or ions much busier, look there first (Numba is installed in the dev environment and works with NumPy 2.4, but isn't a dependency yet).
- `Fold.extend` repeats the *next* modulation's bottom rows above the current column. That is correct for wrapped peaks, but it duplicates everything, so the band is shaded in plots.
- ANDI `global_mass_min/max` widen the m/z axis if present; `total_intensity` in files is ignored (the TIC is recomputed).
- pytest silently keeps only the last of two test functions with the same name. `tests/test_gui.py` once had a duplicated block for this reason, so keep names unique.
- Blob outlines are drawn edge by edge. In the non-extended view, anything above the top is drawn one modulation later and one period lower; each edge must move as a whole, or edges straddling the wrap become full-height lines (`ChromatogramView._draw_overlay`).
- `QSortFilterProxyModel.invalidateFilter()` is deprecated in Qt 6.10; `ResultsPanel._filters` uses `beginFilterChange`/`endFilterChange` when available.
- Single-letter window shortcuts (M, L, E, R, O, 1 to 4, Space) would swallow keys in the Review gallery; Y, N, U and P are handled by the gallery itself, so don't make them window shortcuts.
- `tests/conftest.py` has two synthetic folders: `synthetic_folder` (phase and background) and `cal_folder` (five levels, two samples with known amounts and a 2 m³ volume, one IS, targets A, B, C). Use `cal_folder` for anything 🧪.
- The synthetic GUI folder (`synthetic_folder` in `tests/conftest.py`) adds a noisy rising baseline on m/z 54, which is also the ion of one real peak. Tests that check cleaning compare against that peak's known area (2e5).
- **`fit_alignment`'s "auto" tier picks by leave-one-out (cross-validated) error, never in-sample residual.** The first version compared each tier's fit against its OWN anchors, which is meaningless for the "smooth" tier: a PCHIP curve passes exactly through every anchor it's given by construction, so its in-sample residual is always ~0 regardless of whether it's a sane curve. On 7 real internal-standard anchors spread across a ~2900 s range, this picked a wildly overfit smooth curve with leave-one-out errors of 5 to 58 *seconds* (found while building the demo screenshots below, not by any of the given tests, which happen to use either noiseless synthetic data or too few points for smooth to be eligible). Fixed by scoring every eligible tier with `cross_validate` and, when none clears the "good enough" bar outright, picking whichever has the lowest error relative to its own tolerance rather than just the last (most complex) tier tried. If you touch this selection logic again, test it against several REAL anchors spanning a wide range, not just noiseless synthetic ones — noiseless data can't expose overfitting because there's nothing for the flexible tier to overfit to.
- **`resample_to_reference` fills missing pixels with 0, not NaN.** An early version used NaN for reference pixels with no counterpart in the run (outside its t1 range), which is defensible in isolation, but `np.argmax` on an array whose very first element is NaN returns index 0 regardless of where the real maximum is (NaN poisons the running comparison from the start). `views/compare.py`'s own rendering code already treats missing data as absence-of-signal via `isfinite`/`>0` masks, which 0 satisfies just as well as NaN, so 0 is both test-safe and consistent with how it's actually consumed.
- **`propagate_anchors` needs the anchor's real quantifier ion, not a placeholder.** `AlignState.reference_anchors()` silently drops any anchor with a falsy `ion` (`if p.name not in seen and p.ion`), so seeding anchors by hand with `ion=0` produces an empty search list and batch alignment does nothing, with no error, no failed job, nothing in the log — it just returns early with a status-bar message. If batch alignment finds zero anchors, this is the first thing to check.
- **Switching Compare from Difference to Overlay showed a flat grey rectangle.** `pyqtgraph.ImageItem` remembers the last `levels` (a scalar min/max) it was given and keeps applying them to whatever image comes next, including a 3-channel RGB array from a different mode sharing the same `ImageItem`. Difference sets scalar levels for its diverging colour map; switching straight to Overlay afterwards applied those same scalar levels to the new (already 0 to 1) RGB data, washing it out to one uniform grey. Fixed by passing an explicit `levels=(0.0, 1.0)` whenever RGB data is set (`_ImagePane.show_rgb`). Found only by clicking through the modes in that specific order (Difference then Overlay) while making the milestone 5 screenshots; `test_compare_view_modes` had exercised Overlay but never straight after Difference, and `test_compare_overlay_after_difference_is_not_washed_out` now does. Worth remembering for any other pyqtgraph widget shared between a scalar and an RGB rendering path.
- **`propagate_anchors`'s `run_t1` is a modulation midpoint, not the true apex** — deliberately, since t1 resolution is one modulation wide without finer search. Expect its own leave-one-out error to include roughly ±half a period (here, ±2 s) of quantisation noise on top of any genuine drift; a leave-one-out error of one to two seconds using anchors from `propagate_anchors` is a reasonable, healthy result, not a sign something is wrong.
- **Before rewriting a core module, check whether it (and its dependents) already exist.** Starting this milestone, a from-scratch `core/align.py` was written and nearly shipped before noticing that `gui/align_state.py`, `gui/panels/align.py`, `gui/views/compare.py`, `tests/test_align.py` and the mainwindow wiring already existed, fully built, against a specific (and better-designed) API — `AnchorPoint`/`AlignmentTransform`/`cross_validate`/`propagate_anchors`/`resample_to_reference`, not what got written first. The giveaway was `core/__init__.py` importing names the new file didn't define. The fix was to read the dependents and the test file as the source of truth and rebuild `core/align.py` to match them, rather than adapt everything else to a new design. If a module's dependents already reference a richer API than what you're about to write, that API is the spec — read it first with `find`/`grep` across the whole repo, not just the one file you were asked to build.
- **`BlobSet.labels` (and `.at_pixel`) are in the *extended* frame's row coordinates (offset by `wrap_rows`), not a plain `Fold.image`'s.** A test written against a plain-image pixel row without accounting for the offset silently looked up the wrong blob (or none). `BlobSet.nearest(t1, t2)` and `outline_times`/`footprint` work in true physical coordinates or the blob's own frame consistently; converting a plain image pixel yourself needs `Frame.time_to_pixel`, not a bare `row * pitch`.
- **A vectorised, batched version of an existing per-array statistic (`_robust_sigma` → `_robust_sigma_batch`) can trigger a numpy `RuntimeWarning` (all-NaN slice) on columns whose result is discarded anyway**, when the iterative clipping happens to mask out every value in one column of the batch. Wrapping the call in `warnings.catch_warnings()` looked like a fix but isn't reliable here: this runs inside `find_blobs`, which the GUI calls from worker threads (one per run, `BlobState.run_all`), and Python's warnings filter is process-global, so two threads' `catch_warnings()` blocks can stomp on each other's state. The real fix was to never construct the all-NaN column in the first place (substitute the raw column back in for any group with nothing kept, since its result is discarded via the same mask) — worth remembering for any other "vectorise this per-array loop across a batch dimension" change: prefer avoiding the degenerate input over suppressing the warning it causes, especially near threaded code.
- **When a milestone's placeholder graduates to a real feature, there are usually two greyed-out stand-ins to remove, not one.** Milestone 6 had both a disabled toolbar action (`mainwindow.FUTURE_TOOLS`) and a disabled checkbox in the Layers panel (`panels/__init__.py`'s `LayersPanel.FUTURE`); missing the second would have left a dead, misleading "🔍 Blobs — Milestone 6" checkbox sitting next to the real, working feature. Grep for the milestone number across `gui/` before calling a placeholder cleanup done.
- **`Fold.cube(run, mz=...)` and `Frame.extend` both already work on a 3D (rows, cols, ions) array, not just 2D**, because their array constructions (`img.shape[1:]` in `Fold.extend`, `.reshape(...).transpose(...)` in `Fold.cube`) don't hard-code two dimensions. This made the ion-summed detection surface (milestone 6) a single vectorised `Fold.cube` + one `ndi.gaussian_filter` call with a zero sigma on the ion axis, rather than a Python loop building one image per ion. Worth remembering for milestone 8 (MCR-ALS/NMF/PARAFAC all want a per-ion cube too) and milestone 10 (homologous-series diagnostic ion ratios).
- **`self._action(text, slot, ...)` connects a non-checkable `QAction.triggered` signal directly, and Qt's `triggered(bool checked=false)` always carries that bool argument, checkable or not.** Wiring `act_siloxane = A("🫧 Siloxanes", self.apply_siloxane, ...)` passed `apply_siloxane`'s first positional parameter (`indices`) the literal `False`, which then failed inside with `TypeError: object of type 'bool' has no len()` — never at wiring time, only when the button was actually pressed (or, in a headless test, when `.trigger()` was called), so it slipped past import and even past a first read-through. Every existing action that calls a method taking its own arguments already routes through a no-arg lambda for exactly this reason (`self.act_background = A("🧹 Background", lambda: self.apply_background(), ...)`) — grep for `A(".*", self\.\w+,` (a bare method reference, not a lambda) before adding a new one, and check the pattern next to it rather than assuming a bare method reference is safe because it looks like the simpler option.
- **A GUI value that can come from more than one source needs every reader updated, not just the obvious one.** Adding `RunEntry.siloxane` as a second thing `Project.result_for(i)` can return (alongside `.background`) broke `Renderer._compute`'s S/N view with `AttributeError: 'SiloxaneResult' object has no attribute 'noise'`, because it read `res.noise` assuming `res` was always a `BackgroundResult`. The fix wasn't to add a `.noise` stub to `SiloxaneResult` (S/N is intrinsically a 🧹 concept — "it needs 🧹 on that run, because the noise map comes from background removal" is already true and correct); it was to read `entry.background.noise` specifically wherever noise is needed, in both places it's used (`Renderer._compute` builds the image, `Renderer._key` builds the matching cache key — missing the second would have made S/N sometimes serve a stale cached frame) and in `MainWindow._layers_changed`'s `act_snr.setEnabled(...)` check, which also used to test `result_for(...)  is not None` rather than `entry.background is not None`. Whenever `result_for`/`display_run` grows a new possible source, grep every caller of `result_for` for an assumption that only held for the old one.
- **Phase is never estimated automatically on load unless a target table (with anchors) was also loaded.** `Project._read`'s `done()` only calls `estimate_phases` `if estimate and self.anchors`; without a target table, every run sits at `phase_method="unset"` and `phase=0.0` until `fix_phase()` is called by hand (the 🔄 button), which then falls back to the void/quiet-band method since there are no anchors. This makes sense once you know it (a target table is the only source of anchors), but a GUI test fixture built without one (`tests/conftest.alkane_folder`, which has no reason to carry a target table) needs an explicit `w.fix_phase()` after `open_folder`, unlike `synthetic_folder`-based tests, or `qtbot.waitUntil(lambda: ... phase_method != "unset")` hangs forever with zero jobs running and no error anywhere to explain why.
- **`pg.PolyLineROI.setPoints(points)` followed by `setPos([0, 0])` is the reliable way to place an editable polygon at known, absolute view coordinates**, both for building one (`ChromatogramView.start_stencil_draw`) and for reading one back out in a test (set points, then read `roi.mapToView(handle.pos())` for each handle via `roi.getHandles()` — confirmed to agree with the points passed in). `setPoints` treats its argument as *local* coordinates relative to the ROI's current `pos()`, which is easy to get wrong if `pos()` isn't reset to zero first (points then land offset from where you meant, silently — no error, just a polygon in the wrong place).
- **`pg.ScatterPlotItem.sigClicked` takes three arguments, not two.** It's declared `QtCore.Signal(object, object, object)` and documented as `sigClicked(self, points, ev)` — confirmed by reading pyqtgraph 0.14.0's own `ScatterPlotItem.py`, not guessed. A `lambda points: ...` or `lambda item, points: ...` connected to it raises `TypeError` the moment a user actually clicks a point, never at wiring time or on import, so it's easy to ship (both the PCA and volcano scatter plots in `gui/batch_dialog.py` needed the fix: `lambda _item, points, _ev: ...`). Grep for `sigClicked.connect` before adding a new scatter-click handler and count the lambda's parameters against the source, not against what "feels" like the right signature.
- **A job-progress connection made inside a "run" method, not `__init__`, leaks a new connection on every run.** The first version of `BatchDialog._run_clicked` connected `self.project.jobs.jobChanged` with a fresh lambda every time the button was pressed, so a second run left the first run's (now-defunct) lambda still firing on every subsequent job change, referencing an undefined name that IDE diagnostics caught before it ever ran. The fix, matching how every other one-shot-dialog-with-a-background-job in this codebase should be wired: connect a single bound method once in `__init__` (`self.project.jobs.jobChanged.connect(self._job_changed)`), and filter which job's updates matter with a plain instance attribute (`self._active_job_id`) set fresh at the start of each run, rather than a new closure per run.
- **A redirected PowerShell log file reading as empty is not evidence a command has hung.** `Out-File`/pipe redirection in PowerShell buffers all of a command's output and only writes it out when the command finishes, so polling a log file's size while a long test run is still going will show 0 bytes right up until the moment it completes, even for a run that finishes normally in under a minute. An apparent "hang" investigated this way during milestone 11 turned out to be exactly this (plus, on the very first occurrence, an unrelated stray Python process from a much earlier session, correctly diagnosed via `Get-Process` and killed) — the actual test run had already finished normally both times. Trust the tool's own completion notification (or `run_in_background` plus its callback) over watching a redirected file grow.
- **openpyxl raises on a bare `float('nan')` or `float('inf')` cell value (`ValueError: Cannot convert nan to Excel`), and this repo has plenty of both** (any target that wasn't found or wasn't quantified carries NaN amount/SE/concentration by design, not by accident -- see `SampleResult`). Writing straight from `dataclasses.asdict()` crashes the moment a real "not found" row appears, which none of the milestone's own hand-built test fixtures happened to trigger at first, since it's easy to write only "everything succeeded" sample data. `core/report._clean` strips any non-finite float to `None` (a blank Excel cell) before every write, and `test_write_excel_handles_nan_values_without_raising` exists specifically because this was caught only by deliberately adding a NaN-carrying row, not by the first version of the test suite. Any future writer of tabular dataclass rows into openpyxl (or any format that rejects NaN) needs the same pass.
- **Milestone 10 left one placeholder behind that milestone 12's own cleanup pass caught.** `LayersPanel.FUTURE` (`gui/panels/__init__.py`) still listed `("Stencils", "Milestone 10")` as a permanently-disabled checkbox, long after stencils shipped and worked -- exactly the "two greyed-out stand-ins, not one" gotcha from milestone 6 (this file, above), except this time the second stand-in was missed at the time and only noticed while touching an unrelated part of the GUI two milestones later. Worth a standing habit, not just a one-off fix: grep `gui/` for a milestone's own number *after* declaring it done, not just while building it, since the check is easy to skip when nothing about the current milestone points you at that file.
- **`pyqtgraph.opengl` must be imported after PySide6's own `QApplication` exists, not before.** Importing `pyqtgraph.opengl` (which imports `OpenGL.GL` at its own module level) before `QtWidgets.QApplication` has been constructed raised `ImportError: libshiboken: could not import module 'PySide6.QtGui'` in this environment -- a native-library load-order conflict between PyOpenGL and PySide6's own Qt bindings, not a real missing dependency (reordering the two imports, with nothing else changed, fixed it immediately). `gui/views/surface3d.Surface3DView` imports `pyqtgraph.opengl` lazily inside `__init__`, which is safe in the real app (a `QApplication` always exists before any window is constructed) and in tests (pytest-qt's `qtbot`/`QT_QPA_PLATFORM=offscreen` machinery creates one first) -- but if `pyqtgraph.opengl` (or anything importing `OpenGL.GL`) is ever imported at *module* level anywhere in `gui/`, check it isn't reachable before a `QApplication` exists.
- **An extended-frame pixel's t2 is always `row * pitch`, for any row, in any column -- there is no `wrap_rows` offset to subtract.** This looks like it should need one (`wrap_rows` sizes the extension, after all), but `BlobSet.outline_times` already computes t2 this way with no adjustment, and it's correct: `Frame.extend` only ever *appends* rows on top of the existing `n_rows` (borrowing column *k+1*'s own low rows to show at column *k*'s top, so a wrapped peak's tail displays at its true, longer-than-the-period t2); it never prepends anything below row 0. `wrap_rows` sets how many rows are appended and which band `canonical()` calls the authoritative one per column, not a coordinate shift. `core/overlap.py`'s `BlobCube.t2_of` relies on exactly this (`(row0 + row) * pitch`, no `wrap_rows` term anywhere) -- confirmed by working through `Frame.extend`/`Fold.extend`'s actual row bookkeeping line by line before writing it, not by guessing from the field's name.

## 9. Roadmap, with specs and acceptance tests

The design document gives the reasoning; this is the working summary. Each milestone should add core functions (Qt-free, tested on synthetic and dummy data), then GUI, then GUI tests. Pass marks are proposals to tighten.

**All 12 milestones are done.** Milestone 9 was built last and deliberately out of order: James wanted to try to get a NIST23 licence before building the MS identifier, since it needs a real library to search and to test against (spectral matching against nothing meaningful isn't worth building), so milestones 8 (✂️ overlap toolkit), 10 (⛓️ hydrocarbon and isomer mapper), 11 (🗂️ batch) and 12 (📤 reports and packaging) all went first. In the end 9 was built anyway, against small synthetic libraries with a known answer, on the understanding that a real library would be added afterwards ("I'll add the NIST library later") -- see milestone 9's own write-up below, and check with James whether that library has actually arrived before trusting any of its default thresholds.

### Milestone 4, 🧪 quantification (done)

What was built, against the original spec:
- Target table with qualifier ions and ratios (learned when blank), windows and IS pairing; calibration levels file; `cal_set` and `volume_m3` sequence columns.
- Candidate scoring on position, qualifier ratios and S/N; ambiguity, shared-peak, flank, wrap-edge, off-position and saturation flags. Positions learned from the calibration runs and moved with each run's IS.
- Quantifier-ion volumes with a rim baseline; TIC volumes for every target and every blob.
- Weighted calibration (1, 1/x, 1/x² by relative error), Mandel's test, intercept test, studentised residuals and Cook's distance, LOD/LOQ, inverse-prediction SE. Exclusions need a reason. One set of curves per calibration set.
- Internal standards found in every run, with a trend chart and a tolerance flag.
- All signals: every blob as volume ÷ nearest IS volume, plus semi-quant "as <target>" amounts.
- Review gallery (Y/N/U, P to pick by hand), calibration panel with overrides, results tables with export, peak overlay, undo for every decision, projects that rebuild results on load.
- `pygcgc quant FOLDER` for scripted runs.

Not built from the spec: quantifying a saturated target on a qualifier or M+1 ion (saturation is flagged only), dragging a footprint boundary to re-integrate (picking a different peak is supported), and a process pool (runs are measured in the thread pool). Candidates for a later pass once real data show whether they matter.

**Acceptance on dummy data** (all in `tests/test_quant.py`): every curve passes; isolated quantifier areas within 2% of the truth; sample amounts for isolated targets within 10%; saturation flagged at the top levels; the anthracene interferent flagged by the qualifier check.

**Addendum: calibration-set bracketing (also done).** James asked for multiple calibration sequences (e.g. a block at the start of the week and another at the end) with drift corrected by interpolating between them, which the original spec had left as future work. `bracket_cal_sets` finds the two calibration sets either side of a sample by run order (each set's position is the mean index of its own calibration runs); `blended_amount` reads the sample's response against both curves and blends the two amounts by how far along it sits (the bracketing-standard method). A sample with its own `cal_set` still uses that set exactly, with no blending; one outside every set is flagged as extrapolated and uses the nearest one alone. `QuantSettings.interpolate_cal_sets` (default on) and `pygcgc quant --no-interpolate` turn it off, falling back to "own set, else the most recent one before it". Tested against a real two-block synthetic sequence (`drift_folder` in `conftest.py`) run through the actual `pygcgc quant` CLI, confirming the blended amount beats either single calibration alone.

### Milestone 5, 📍 alignment and compare (done)

What was built, against the original spec below: everything, with three simplifications. Anchor clicks use the clicked pixel directly rather than snapping to a peak's intensity-weighted centre (fine at this resolution; revisit if real data show it matters). Batch anchor-finding (`propagate_anchors`) searches for each named anchor independently, by ion and window (the same search `locate_anchor` uses for phase), rather than a full Hungarian-plus-RANSAC match across every blob in the run — a much cheaper approach that works well when you already know what you're looking for (internal standards, named targets), which is the common case; the fuller blob-matching version is better placed after milestone 6 gives blob detection its own upgrade. There's no small-multiples XIC gallery yet. The difference compare mode scales by the median ratio of the two images' brightest shared pixels (`views/compare.robust_scale`) rather than a full Theil-Sen fit restricted to internal-standard pixels specifically — simpler, and robust to the same problem (a run that's just more concentrated shouldn't look like a wall of difference).

**How the pieces fit together:** `core/align.py` is Qt-free (fitting, cross-validation, propagation, resampling). `gui/align_state.py` (`AlignState`) holds the reference run name, every run's anchors and fitted transform, owned by `Project` as `project.align`. `gui/panels/align.py` is the anchor table and controls; `gui/views/compare.py` is the four compare modes, driven by a plain `image_source(index) -> (image, t1, pitch, period, label) | None` callback the main window supplies (`_compare_image`), so neither panel needs to know about folds or the render cache. `Renderer` gained an `aligned` flag (`set_aligned`, `aligned_available`); when it's on and the current run isn't the reference, the renderer resamples through `AlignState.image_for` instead of building the run's own image, and split/S/N are disabled together with it (they don't make sense on a resampled image with no matching raw/noise data of its own).

**Acceptance on dummy data:** not yet exercised against the dummy pack specifically (the synthetic tests in `tests/test_align.py` cover the maths precisely, with known ground truth). Worth adding once real data arrive: fit a transform between two dummy calibration runs and check the leave-one-out error and that difference-mode residues around the internal standards shrink relative to no alignment.

### Milestone 5 spec, as originally written (for reference)

- **Anchor mode (A).** Click a peak in the reference run, then in the target run. Clicks snap to the intensity-weighted centre above half height. Internal standards and n-alkanes are suggested as anchors.
- **Transform, growing with the number of anchors.**
  - 1 anchor: a shift.
  - 3 or more: affine.
  - 6 or more: a monotone PCHIP curve for t₁, with a smoothing spline for the t₂ shift along t₁.
  - Fit with a Huber loss, and choose the model by leave-one-out RMSE. Check that the t₁ map increases monotonically.
  - Resample per ion via the inverse map (`map_coordinates`), respecting the t₂ wrap.
- **Batch.** Search for the anchors automatically, then optionally refine with Hungarian matching of blobs and a RANSAC fit.
- **Compare modes.**
  - Blink (B)
  - A grid of 2 to 9 runs with linked axes
  - Difference, scaled by a Theil–Sen fit on internal standard pixels
  - Overlay in magenta and green
  - An XIC gallery
- **Acceptance.** Leave-one-out error under 0.5 s in t₁ on the dummy samples, and blank-subtraction residues shrink after alignment.

### Milestone 6, 🔍 blob detection (done)

What was built, against the original spec below: everything, with the simplifications noted inline.

- **Image and seeds.** The detection surface is the pixel-wise *maximum* of the plain smoothed-TIC S/N (as before) and the sum of every ion's own S/N image, rather than the ion-sum alone. An ion counts if it has at least `min_ion_points` stored points at all (`_active_ion_cube`, via `Fold.cube` — a single vectorised bincount over every qualifying ion at once, not a Python loop); its own image is smoothed and divided by its own column-block noise (`_column_noise_batch`/`_robust_sigma_batch`, the batched form of the existing single-ion `_column_noise`/`_robust_sigma`, computed for every ion and every t1 block in one vectorised pass rather than looping). Taking the max rather than switching over entirely means nothing the old, TIC-only method already found is ever lost; a peak that's faint on every individual ion but consistent across several can now also be found (`test_a_peak_too_narrow_for_one_ion_alone_is_still_found_by_the_ion_sum`). Seeding, the watershed and the `blob_rel_floor` trim are otherwise unchanged from the original version.
- **Properties per blob.** Volume, height, S/N, number of modulations spanned and the summed spectrum already existed. Added: `width_t1`/`width_t2` (FWHM, from the footprint's own unsmoothed column/row profiles — exact for a Gaussian peak, `test_widths_and_apex_spectrum` checks it to within 10% on synthetic data) and `apex_spectra` (the spectrum of the scan(s) nearest the single apex pixel, for a later library search, as distinct from the noisier footprint-summed spectrum). The apex itself is still the existing intensity-weighted t1 centroid plus a parabolic t2 refinement, not a 2D quadratic fit — the centroid already handles asymmetric peaks better than a parabola would, and revisiting it wasn't asked for.
- **Co-elution flag.** `scipy.cluster.hierarchy.fclusterdata` (single-linkage, a distance threshold) rather than DBSCAN, to avoid adding scikit-learn as a dependency for one clustering call; for a handful of points per blob the two behave alike. Every ion holding at least `coelution_frac` (5%) of a blob's spectrum gets its own local apex pixel inside the footprint; more than one cluster (units: one modulation along t1, two rows along t2) flags it. This is an untested heuristic — real co-eluting compounds haven't been seen yet.
- **Speed.** The per-ion image-and-noise step turned out to be the part worth vectorising (see above), not worth chunking: `Fold.cube` builds every qualifying ion's image in one call, and a single `ndi.gaussian_filter` with a zero sigma on the ion axis smooths all of them in one call too. Seeding and the watershed *are* chunked: `_chunk_bounds` splits a long run into overlapping stretches of t1, `_segment_chunk` runs the same seed-and-watershed logic as before on each piece (via `ThreadPoolExecutor` when there's more than one), and a peak is kept exactly once, by whichever chunk's *core* (non-overlap) region its seed falls in. Correctness depends on the overlap being wider than any real peak — the default (15 modulations) comfortably covers everything in the synthetic tests; `test_chunked_processing_matches_unchunked_on_a_long_run` checks a chunked and an unchunked run agree exactly on a 1000-modulation synthetic run. A short run (every test run so far, and the dummy pack) falls into a single chunk and runs the pre-chunking code path unchanged.
- **Editing.** `delete_blobs`, `merge_blobs` and `add_blob_at` in `core/peaks.py`, all Qt-free and tested on synthetic data before any GUI existed. Delete and merge need only the existing `BlobSet` (no `Run`/`Fold`): delete zeroes a footprint's label pixels and renumbers; merge is an *exact* combination for volume, pixel count, modulations spanned and the summed spectrum (footprints never overlap, so nothing is double-counted) and an exact combined position and width via the parallel-axis theorem, from each blob's own position/width/volume — no need to re-read the raw pixels. Add does need `Run`/`Fold`: it grows a fresh footprint from the clicked pixel (refined to the tallest nearby TIC pixel) by the same watershed the main detector uses, refusing a click that already belongs to a blob.
- **GUI.** `gui/blob_state.py` (`BlobState`, owned by `Project` as `project.blobs`) runs `find_blobs` per run as a background job and keeps the result; `gui/panels/blobs.py` is the table (add/delete/merge buttons, G for merge); a second, independent overlay channel in `views/image2d.py` (amber, alongside the existing cyan 🧪 one) draws every footprint plus a bold highlight for the selected ones, and a plain click on the 2D view selects the nearest blob in the table when the overlay is shown (`MainWindow._select_blob_at`) — the "linked both ways" the spec asked for. Add reuses the same one-click "start picking, then `_point_clicked` finishes it" flow as 📍 add anchor and 🧪 pick a peak. Every edit is undoable (`EditBlobs`, the same before/after-snapshot shape as `EditAlignment`).
  - **Not built:** dragging or otherwise editing a footprint's outline directly (only whole-blob delete/merge/add); a settings dialog for `PeakSettings` (the defaults apply everywhere). Both are candidates once real data show whether they're worth it.
- **Also.** Blank subtraction (`core/background.py`) now scales each ion's artefacts separately: `scipy.ndimage.label` on the blank's own "significant" pixels finds connected regions per ion (deliberately not the TIC-blob machinery above — a per-*ion* connected component is simpler, needs no cross-module plumbing, and is exactly the right shape for the stated problem, since two artefacts on one ion that vary independently are, by definition, in different regions of that ion's own image), each gets its own sample/blank ratio, and whatever significant signal isn't part of any region still falls back to one scale for the ion as a whole (the old behaviour, and what a single-region ion reduces to exactly). `test_blank_subtraction_scales_two_artefacts_on_one_ion_independently` puts two artefacts on one ion that need opposite corrections and checks both come out clean, which the single shared factor could not have done.

**Acceptance on dummy data:** not yet exercised against the dummy pack specifically (all the acceptance tests above are on synthetic data with known ground truth, following the pattern of milestone 5). Worth adding once real data arrive: `find_blobs` on a real cleaned run, checking that known targets are (still) found as blobs and that the co-elution flag actually fires on a genuinely co-eluting pair.

### Milestone 7, 🫧 siloxane remover (done)

What was built, against the original spec below: everything, with one addition beyond it.

- **Flag.** `core/siloxane.siloxane_score`/`siloxane_scores`/`flag_siloxane_blobs`, exactly the formula specified: fraction of a blob's volume on the siloxane ions, times cosine similarity to `SILOXANE_REFERENCE`. A blob needs at least `min_ions_present` (3) of them to show any signal at all before it's scored, so a blob with one or two ions overlapping the list by coincidence scores 0 rather than an artificially high cosine from too few dimensions. **The ROC threshold wasn't chosen** -- no real or dummy data has been available to build one from (nothing has touched real data yet, and the dummy pack isn't present in this environment either). `score_threshold` (0.3) is a reasonable guess instead, called out as provisional in the module docstring, README and the settings dataclass itself; `test_dummy_siloxane_score_separates_real_targets_from_planted_siloxanes` (`tests/test_siloxane.py`) is written and marked `@pytest.mark.dummy`, ready to be the actual ROC check the day the dummy pack (or real data) turns up -- run it before trusting the default on anything real.
- **Remove.** `core/siloxane.remove_siloxanes`, per pixel, exactly as specified (NNLS on the siloxane ions; a single reference makes this a closed-form clipped projection, `c = max(0, obs·ref / ref·ref)`; only `min(c·ref, obs)` is ever taken, never a whole ion). **One addition beyond the spec:** a pixel is only fit at all if its own ion ratios resemble the reference (cosine ≥ `min_fit_cosine`, 0.8), not merely if enough of the listed ions happen to have signal. Without this, a real three-ion coincidence in the wrong proportions (built to check exactly this: `test_a_real_coincidence_in_the_wrong_ratio_is_not_removed`) got its dominant ion (the one with the largest reference weight) subtracted down to nothing, because a least-squares fit across a handful of ions is pulled toward whichever ion the reference weights most, regardless of whether the *ratios* actually match. The "presence count" gate alone (matching the spec literally) isn't enough to protect a coincidental overlap; the ratio gate is. Behenic acid itself needed no such protection -- it fails the presence-count gate outright (only one ion, m/z 73, ever has signal there), so the ratio gate is pure extra safety for other cases, not what makes the milestone's own acceptance test pass.
- **Acceptance.** `test_remove_siloxanes_strips_the_pattern_but_keeps_the_isolated_analyte` (synthetic): the reference-shaped peak loses over 90% of its volume, the isolated single-ion peak (standing in for behenic acid) keeps its full volume, comfortably inside the 5% bar.

**How the pieces fit together:** `core/siloxane.py` is Qt-free, and doesn't import `core/peaks.py` for the removal path at all -- `remove_siloxanes` needs only `Run`/`Fold` (via `Fold.cube`, as milestone 6's ion-summed detection also uses) and never touches a `BlobSet`; only the *flagging* functions take one, for the "score each blob" half of the spec. In the GUI, 🫧 isn't its own state class (see section 5): `Project.siloxane_settings`/`RunEntry.siloxane`/`compute_siloxane`/`set_siloxanes` follow 🧹's own shape directly, `ApplySiloxane` is the undo command (same before/after-snapshot shape as `ApplyBackground`), and flagging surfaces into the *existing* 🔍 Blobs panel as one more column (`flag_siloxane_blobs` computed fresh in `MainWindow._blobs_changed`, not stored) rather than a new panel of its own -- there's nothing else to show for a flag beyond "which blobs, on this run".

**Not built:** a settings dialog for `SiloxaneSettings` (defaults apply everywhere, same cut as 🔍's `PeakSettings`); automatic re-fitting when 🧹 or the fold changes underneath an applied 🫧 layer (it's cleared instead -- see section 5); wiring into 🧪's own measurement (`quantstate.py` still reads `entry.background` directly, so quantified amounts don't reflect 🫧 even when it's been applied and is visible in the view). All three are candidates once real data show whether they matter enough to build.

### Milestone 8, ✂️ overlap toolkit and 3D view (done)

What was built, against the original spec below: every tool, with two deliberate simplifications (NMF was skipped since MCR-ALS already covers the same ground here; PARAFAC2 was skipped entirely) and one dependency swap (no `pyMCR` or `TensorLy` -- both are hand-written on plain numpy/scipy, the same call this project has made every other time a well-known method was small enough to implement directly: PCA via SVD, Westgard's rules, the co-elution clustering).

- **The cube.** `core/overlap.blob_cube` reads a small (rows, cols, ions) window around one blob, for whichever of its own ions actually carry its signal (`OverlapSettings.ion_share_min`, falling back to the top `min_ions` if too few clear it). Everything else in the module works from one of these (`BlobCube`), so a run and a fold are only ever read once per blob, and every method sees the same data.
- **Unique-ion apex map.** `unique_ion_apexes`: each ion's own local apex inside the footprint, clustered (single-linkage, the same `coelution_gap` units 🔍's own co-elution flag uses). More than one cluster is the cheapest possible sign of more than one compound.
- **Geometric splits.** `split_by_line` (a straight cut through two points), `split_by_watershed` (a fresh watershed seeded wherever you say the apexes are, on the cube's own summed image), `split_by_valley` (`skimage.graph.route_through_array`, the lowest-intensity route between two points -- the boundary a watershed would find on its own, made explicit). `split_volumes` sums each labelled region.
- **Joint peak-shape fit.** `fit_overlap`: k 2D shapes (Gaussian, or an EMG along t1 for a tailing peak) times mass spectra, fitted by variable projection. Shape parameters are the nonlinear unknowns; at every trial set, each component's spectrum and optional constant or bilinear local background are solved by weighted non-negative least squares (`scipy.optimize.nnls`), and `scipy.optimize.least_squares` handles the bounded outer search. The same Poisson-style weights are used throughout, repeated starts are supported, BIC counts shape and spectral/background coefficients, and component signal includes the fitted shape integral. `predict_overlap` reconstructs held-out pixels and `cross_validate_overlap` reports spatial-block error. Parameter uncertainty (`OverlapComponent.row0_se`/`col0_se`) comes from the fit's Jacobian.
- **MCR-ALS.** `mcr_als`: alternating non-negative least squares recovers a free-form elution profile and a free-form spectrum for each of k components, no peak shape assumed. `unimodal=True` (the default) additionally caps each component's own concentration map toward its own peak along both axes (`_enforce_unimodal`/`_unimodal_1d`) -- a simple, well-defined "capped toward the peak" projection, not the exact least-squares-optimal isotonic-regression one a dedicated MCR package would use, but enough to stop a component inventing a second bump. `mcr_restarts` matches spectra across repeated starts and reports convergence, explained variance and stability. NMF wasn't built separately: with a non-negativity constraint already in place, MCR-ALS *is* NMF plus the optional unimodality constraint, so a second, parallel implementation would have added nothing.
- **PARAFAC across runs.** `parafac`: a basic trilinear (CP) decomposition by alternating least squares (Khatri-Rao unfolding, `nnls` row-by-row for genuine non-negativity rather than a plain least squares followed by clipping). `core_consistency` (Bro and Kiers, 2003) and `split_half_stability` (a greedy best-correlation match between two random-half fits) are the two standard diagnostics for whether a chosen number of components is actually trustworthy. `build_run_tensor` builds the (run, elution position, ion) array PARAFAC needs from a matched feature, by bilinear interpolation (`scipy.ndimage.map_coordinates`) of each run's own folded ion image at the same absolute (t1, t2) window -- this assumes retention times are already comparable across runs (true of a batch that's already phase-corrected to one method), not a full geometric alignment. **PARAFAC2 was not built** (see section 7): it would additionally tolerate each run having its own elution-time shift, which needs materially more machinery than three factor matrices, and there was no real multi-run drift to test it against.
- **3D view.** `gui/views/surface3d.Surface3DView` wraps `pyqtgraph.opengl.GLViewWidget`/`GLSurfacePlotItem`, coloured by height with the app's own magma colour map (`pg.colormap.get("magma")`, already bundled with pyqtgraph -- no new dependency for the colour, only for the OpenGL rendering itself, `PyOpenGL`, newly added to the `gui` extra). Falls back to a plain explanatory label if `PyOpenGL` isn't installed, importing `pyqtgraph.opengl` lazily so the rest of the app is unaffected either way (see section 8 for the import-order gotcha this surfaced).
- **GUI.** `gui/overlap_dialog.OverlapDialog`: a blob picker (co-eluting ones, 🔍's own flag, listed first), the 3D surface, the unique-ion map with a one-click "split at each cluster's own apex" button, and tabs for the peak-shape fit and MCR-ALS (both run through `project.jobs`, like every other potentially-slow action in this app). No GUI state class (section 5) -- like 🗂️, it's a one-shot, read-only analysis.
  - **Not built:** a way to draw a line or valley-path split by hand in the 2D view (`split_by_line`/`split_by_valley` are real, tested, and callable from Python -- just not wired to a drawing tool, the same "core exists, no button yet" cut milestone 10 made for `find_homologous_series`); a GUI entry point for PARAFAC across runs (needs a "pick the same feature across several runs" flow this dialog, tied to one run at a time, doesn't have -- a natural fit for a future action on the batch dialog instead, where several runs are already in view together).

**How the pieces fit together:** `core/overlap.py` is Qt-free and imports only `core/fold.py`, `core/peaks.py` (for `BlobSet`/`Frame`) and `core/run.py` -- no other core module needed changing. `gui/overlap_dialog.py` and `gui/views/surface3d.py` are the only new GUI files; `gui/mainwindow.py` wires a toolbar/menu action (`show_overlap_dialog`) that hands the dialog whichever run is currently open, the same shape `show_batch_dialog` already uses.

**Acceptance and current evidence.** `tests/test_overlap.py` now has 28 tests covering the original split, fit, MCR and PARAFAC cases plus weighted fitting, analytic and measured-template peak models, signed background surfaces, repeated-start stability, prediction, spatial cross-validation and known-area recovery. GUI tests exercise the dialog end to end. The supplied real acquisition has also been audited near 15 min / 1.2 s: BIC, ion-apex clusters and repeatable MCR support two mathematical factors, while a third factor is unstable. An ideal-profile software-copy benchmark in real background recovers both areas within 10% in 4 of 9 conditions. The movable n-C16 template passes 9 of 9 signal-only cases and 6 of 9 in the chosen real background; all 10%-minor cases fail. This is evidence for the machinery and a limited operating envelope, not acceptance against identified co-eluting standards such as BbF/BkF or benz[a]anthracene/chrysene; see `docs/BLOB_DIAGNOSIS_AND_PLAN.md`.

### Milestone 9, retention index and 🏷️ MS identifier (done, but never seen a real library)

What was built, against the original spec below: everything, but tested only against small, hand-built synthetic libraries -- James still plans to add a NIST23 (or other) library later, and none was available while building this. Treat every score weight, threshold and tier boundary as a reasonable placeholder, the same caveat 🫧's `score_threshold` has carried since milestone 7.

- **Retention index.** Already built in milestone 10, as the spec itself anticipated: `retention_index` (`core/identify.py`) is a one-line wrapper around `AlkaneSeries.carbon_of(t1) * 100`. Nothing new needed here.
- **Library.** `load_msp`/`write_msp` (`core/identify.py`) parse and write the common NIST/MoNA/MassBank MSP text format (`Key: value` metadata, `Num Peaks:`, then that many `mz intensity` lines) -- lenient about field-name spelling (`RI:`/`RetentionIndex:`/`Retention_Index:`/...) and semicolon-packed multi-pair peak lines, since real exports vary and none was to hand to check against. `build_library` packs every entry's spectrum into one sparse (entries, unit mass) `scipy.sparse.csr_matrix`, as the spec's own "store as a sparse unit-mass matrix" asked for, and precomputes each entry's own top ions once, at load time.
- **Search.** `search`: two cheap prefilters (an RI window; at least one shared "top ion" between query and candidate) before any real scoring, since a full weighted-dot-product comparison against every library entry, for every blob, is the part that would actually be slow against a real multi-thousand-compound library. What's left is scored with a forward and reverse weighted dot product (Stein and Scott, 1994 intensity/mass weighting exponents, `weight_a`/`weight_b`), a peak-overlap ratio (the spec's own "ratio term"), combined and then reduced by an RI penalty that grows with `|query RI - library RI|`. Reverse scoring only looks at mass channels the *library* entry has something on, which matters when the query spectrum carries a co-eluting neighbour's peaks too (the exact scenario ✂️ resolves in milestone 8 -- the two milestones complement each other: ✂️ pulls a mixed spectrum apart, 🏷️ names what's left).
- **Confidence.** `assign_qvalues`: target-decoy competition across a whole run's worth of best hits at once (see section 7 for why it has to be batch-level, not per query), `generate_decoys` building one shuffled decoy per real library entry (same mass channels, reassigned intensities, same RI) so a q-value can be estimated even from a library that carries no decoys of its own. `classify`: a simplified reading of Schymanski and colleagues (2014) -- only tiers 2a ("probable structure", library match plus unambiguous RI confirmation), 2b (library match alone) and 3 ("tentative candidate") are reachable from a unit-mass EI spectrum plus RI; levels 1 and 4 are out of reach for the reasons in section 7.
- **Other features.** `promote_to_target`: a confident hit becomes a `Target` row (quantifier/qualifier ions read from the library entry's own strongest peaks, position from where it was actually found, not the library's own reference run), written out with the new `core/targets.write_targets_csv` (append or fresh file) for the target table to pick up next reload. `build_inhouse_entry`: the reverse direction, turning an accepted standard's own apex spectrum into a fresh `LibraryEntry`, so a real, reusable library grows from standards run on this instrument over time -- `write_msp` persists it.
- **GUI.** `gui/identify_dialog.IdentifyDialog`: load an MSP library (with an "auto-generate decoys" checkbox), "🏷️ Identify blobs" runs the whole-run search through `project.jobs`, a results table shows every blob's best hit with its score/RI/tier/q-value, and "Promote to target…"/"Add to in-house library…" write files (see section 5 for why they write rather than mutate live Project state). No GUI state class -- like ✂️ and 🗂️, it's a one-shot, read-only analysis dialog.
  - **Not built:** a settings dialog for `IdentifySettings` (defaults apply everywhere, the same cut every module without one has made); a way to browse or edit a loaded library's own entries; genuine Schymanski levels 1 and 4.

**How the pieces fit together:** `core/identify.py` is Qt-free and imports `core/hydrocarbons.py` (for `AlkaneSeries`, the RI source), `core/peaks.py` (for `BlobSet`) and `core/targets.py` (for `Target`, and the new `write_targets_csv` lives in `targets.py` itself, not `identify.py`, since the target-table CSV format is `targets.py`'s to own). `gui/identify_dialog.py` is the only new GUI file; `gui/mainwindow.py` wires a toolbar/menu action (`show_identify_dialog`) that hands the dialog whichever run is currently open plus its own alkane series (`self.hydrocarbons.series_for(self.index)`), the same shape `show_overlap_dialog` and `show_batch_dialog` already use.

**Acceptance on synthetic data** (`tests/test_identify.py`, 21 tests): MSP files round-trip through `write_msp`/`load_msp` exactly, including several real-world field-name variants and multi-pair peak lines; searching a spectrum against its own library entry scores forward and reverse near 1.0 and comes back as the top hit; two library entries sharing an *identical* spectrum but different RI (standing in for phenanthrene/anthracene) are correctly told apart by the RI penalty in either direction -- the spec's own named acceptance case; target-decoy competition gives genuine hits q-values at or below 0.05 and never lets q improve in the wrong direction down a ranked list; on ten synthetic compounds with a known identity, `identify_blobs` recovers at least 90% correctly (the spec's own numeric bar) even with some of them perturbed by intensity noise; `promote_to_target` and `write_targets_csv` round-trip through `load_targets` intact. A test marked `@pytest.mark.dummy` (skipped in this environment) is ready against the dummy pack's own `synthetic_library.msp`, checking the same 90%-correct bar on whichever already-confirmed target names line up with the library's own naming -- written defensively (it skips rather than guesses if too few names match) since there was no dummy pack available to check the real naming against. **A real library (NIST or otherwise) has not been tried at all.**

### Milestone 10, ⛓️ hydrocarbon and isomer mapper (done)

What was built, against the original spec below, plus one feature James asked for directly that the spec hadn't anticipated: an easy way to build a stencil frame once, on the alkane standard, and carry it onto every sample without redrawing it.

- **The coordinate system (not in the original spec, but everything else depends on it).** A group-type stencil only means the same thing on two different runs if it's described relative to something both runs have in common, and the one thing you can always find with confidence is the alkane ladder. `AlkaneSeries` (in `core/hydrocarbons.py`) gives that: `to_relative(t1, t2)` -> (carbon-number-equivalent, t2 offset from the alkane line's own position at that carbon) and `to_absolute` the inverse, against *any* run's own found ladder. This is what makes "lift" possible at all; it's also, incidentally, the Van den Dool interpolation milestone 9's spec asks for (see above).
- **n-Alkane finder.** `find_alkane_series(run, fold, seeds, settings)`: two confirmed (carbon, t1, t2) points predict the rest by linear spacing, each prediction is searched for with `phase.locate_anchor` (see section 8's gotcha on why that, not a bespoke search, was the right call), and the fit refits and refills gaps for `refine_passes` rounds. Confirmation is by qualifier ratios (71/85 relative to 57) reported on the hit, **not enforced as a hard gate** -- alkane fragmentation ratios vary enough by chain length and instrument that a strict quantitative check risked rejecting real hits sight unseen, with nothing but synthetic data to calibrate a threshold against. Revisit once real data show whether that's too permissive. The spec's "confirms... with... the molecular ion" wasn't built: at typical alkane masses (C10 upward, M+ well above 140) that's often outside a unit-mass BenchTOF's practical range or too weak to rely on, and the qualifier-ratio check already does the useful part of the job.
- **Propagation.** `propagate_alkane_series(reference, run, fold, settings)`, one function, not built into the finder: searches each of the reference's own confirmed carbons near the reference's own position in the new run, the same simplification `align.propagate_anchors` already makes for internal standards (retention drifts a little, not by a whole modulation).
- **Homologous series.** `find_homologous_series(blobs, ion_pair, series, settings)`: a small, exhaustive stand-in for RANSAC (try every candidate blob in turn as the reference phase, keep whichever explains the most of the rest), using the alkane ladder's own per-carbon spacing as the step-size prior rather than fitting one from scratch -- reasonable because every CH2-adding series climbs t1 at close to the same rate as the alkanes do. The specific diagnostic ion pairs named in the spec (91/105, 82/83, 142/156, 58/59) are supported as *inputs* (`ion_pair` is just a (major, minor) tuple) but none is hardcoded or validated against real data; picking the right pair per compound class is chemistry knowledge to confirm with James, not something to guess at without real data.
- **Stencils.** `Stencil` (a polygon in the coordinate system above, plus a response factor), `stencil_from_polygon` (record one drawn in real t1/t2 against a run's own series), `Stencil.to_absolute` (read it back out against any series -- the "lift"), `stencil_totals` (point-in-polygon apex test against a `BlobSet`, summed TIC volume). `StencilSet` is the "frame": one named collection, saved with the project (unlike the alkane series itself, which isn't -- see section 5).
- **Markers.** `find_markers`: pristane and phytane, at a fixed carbon-equivalent offset (-0.3, provisional) before n-C17 and n-C18 respectively. Genuinely just a lookup by position; there's no diagnostic-ion distinction from the alkanes themselves in this first version (see HANDOVER.md's questions for James).
- **GUI.** `gui/hydrocarbon_state.HydrocarbonState` (find/propagate as background jobs; stencils as the undoable edit layer, `EditHydrocarbons`); `gui/panels/hydrocarbons.py` (alkane table, stencil table with an inline-editable response factor column, markers readout); a stencil is drawn with `pg.PolyLineROI` on the 2D view (`ChromatogramView.start_stencil_draw`/`stencil_vertices`) and its lifted outlines are a third, independent overlay channel alongside 🧪's and 🔍's (`set_stencil_overlay`). The two-click alkane flow reuses the same "start picking, `_point_clicked` finishes it" shape as 📍 add anchor, 🧪 pick a peak and 🔍 add blob, with a modal `QInputDialog.getInt` after each click for the carbon number (the same "pop a small dialog mid-flow" pattern the calibration panel's exclude-reason prompt already uses).
  - **Not built:** editing a saved stencil's shape (delete and redraw instead); a GUI entry point for `find_homologous_series` (it's real, tested, and usable from Python, just not wired to a button yet); re-finding the alkane series automatically when 🧹 or the fold changes underneath it (find or propagate again by hand, the same cut as 🫧, for the same reason -- see section 5).

**Acceptance on synthetic data** (`tests/test_hydrocarbons.py`, 10 tests): a 16-alkane synthetic ladder (C10-C25, drifting t2) is found from two seeds with exact spacing recovered; `carbon_of`/`t1_of` round-trip to within 1e-6 and extrapolate correctly beyond the confirmed range; propagation onto a run shifted +6 s in t1 and +0.03 s in t2 finds every carbon within one modulation; a stencil built on the reference run and lifted onto that shifted run finds the *same* blob count and volume (within 5%) as drawing it fresh would; a genuine homologous series (a parallel branched-alkane band on a different ion) is fully recovered; a real three-ion coincidence in the wrong ratio does *not* get mistaken for one. Not yet exercised against the dummy pack -- worth doing once it's available, particularly the qualifier-ratio confirmation and the marker offsets, both of which are currently unvalidated guesses.

### Milestone 11, 🗂️ batch (done)

What was built, against the original spec below: everything, with the simplifications noted inline.

- **Pipeline.** `core/batch.py`. `BatchConfig` (period, settings, reference run, the two volcano groups) is the saved pipeline JSON, with `.save`/`.load`. `StepCache` hashes each step's inputs and settings to a pickle file on disk (background, then optionally 🫧, then optionally 🔍, each keyed on the previous step's key plus its own settings' `to_dict()`), so changing one setting invalidates that step and everything after it but nothing before it, and an interrupted batch resumes automatically just by re-running it (everything already cached loads back instead of recomputing). `max_workers > 1` runs `_prep_one` (a top-level, picklable function, required for Windows' `spawn`-based multiprocessing) across a real `ProcessPoolExecutor`, not a thread pool -- this is genuinely CPU-bound per-run work, not something waiting on I/O or the GIL. `max_workers <= 1` runs the identical function in a plain for-loop instead, both because it avoids process-pool overhead for the common single-worker/testing case and because it's what every test in `test_batch.py` uses for speed and determinism. One run failing (`try`/`except` around each `as_completed` result) is recorded in `BatchResult.errors` by name rather than aborting the rest. `pygcgc batch FOLDER` runs it from the command line, with `--config`/`--save-config` for the JSON pipeline file.
- **Cross-run outputs.** `build_feature_table` takes a reference run's own blobs as the feature list and matches every other run's blobs onto them by `scipy.optimize.linear_sum_assignment` (the Hungarian algorithm) on a scaled t1/t2 distance, same 60 s-of-t1-to-0.5 s-of-t2 scaling 🧪's own "nearest" already uses. A run with nothing close enough to a feature (`max_distance`) isn't left blank: `_box_sum` integrates a small fixed window of that run's own TIC directly at the reference position, so "not detected" reads as an honest near-zero number rather than a gap. `westgard_flags` implements the standard six rules (1-2s, 1-3s, 2-2s, R-4s, 4-1s, 10x) over one feature's values across the batch, shown as a control chart with mean/±2SD/±3SD lines in the dialog.
- **Statistics.** `pca`: log1p, then autoscale (mean-centre, unit-variance per feature), then plain `np.linalg.svd` -- no new dependency for something this small. `volcano`: Welch's t-test (`scipy.stats.ttest_ind(..., equal_var=False)`) per feature between two chosen groups of runs (skipping any feature without at least `min_group` nonzero values in both groups), log2 fold change with a +1 offset to survive zeros, and a hand-written Benjamini-Hochberg FDR correction across every feature actually tested.
- **Navigation.** `BatchDialog.navigateRequested` (a `(run_name, t1, t2)` signal) fires from a double-clicked feature-table cell or a clicked PCA/volcano point; `MainWindow._batch_navigate` switches to that run if it's open and centres the 2D view there, or tells the user to open it first if it isn't, exactly the "jump to it" the spec asked for.
- **GUI.** `gui/batch_dialog.BatchDialog`: a folder picker, run/siloxane/blobs/quant checkboxes and a worker-count spinner, a status line driven by the existing `JobManager` (`project.jobs.submit`, so it's cancellable and shows in the Jobs panel like every other background operation), and four tabs (feature table, QC chart with a per-feature combo box, PCA scatter, and volcano with two multi-select run lists for the groups). It lives directly on `MainWindow` as `self.batch_dialog`, created on first use, not part of `Project` (see section 5 for why).
  - **Not built:** a settings dialog beyond the four checkboxes and worker count (every module's own defaults apply, the same cut every other milestone without a settings dialog has made); a GUI reference-run picker (defaults to the first run with blobs; the CLI's `--reference` covers it for scripted use); a real per-run progress bar (one job message, "N of M", not a bar per run).

**How the pieces fit together:** `core/batch.py` is Qt-free and imports every other core module it orchestrates (`background`, `siloxane`, `peaks`, `quant`, `phase`, `targets`) but reimplements none of them -- see section 7 for why quantification specifically is reused rather than rebuilt. `gui/batch_dialog.py` is the only GUI file the milestone needed; there's no new state class (section 5) and no new undo command, since there's nothing here to undo.

**Acceptance on synthetic data** (`tests/test_batch.py`, 13 tests): a full run over `cal_folder` (5 calibration levels, 2 samples) caches correctly (a second run makes zero calls to `remove_background`/`find_blobs`) and produces a feature table and a quant report; changing `PeakSettings` recomputes blobs for every run but leaves background untouched; one run's background step raising an exception still leaves the other six prepped; `BatchConfig` round-trips through JSON; all six Westgard rules fire on data engineered to trip them and stay quiet on unremarkable noise; PCA separates two runs that agree from a third that doesn't; a volcano test plants a real difference in three of twenty features and recovers exactly those three at q < 0.05, with the correct fold-change sign; the CLI runs a full batch and writes all five output CSVs, and a config file saved by one CLI invocation reproduces the same settings in a second. GUI coverage in `test_gui.py` (3 tests) exercises the dialog end to end against the app's own synthetic fixture (run, fill all four tabs, select volcano groups) and the navigate-or-say-so behaviour. Not yet exercised against the dummy pack or real data -- worth doing once either is available, particularly whether the fixed feature-matching radius and gap-fill window need to scale with real peak widths.

### Milestone 11 spec, as originally written (for reference)
